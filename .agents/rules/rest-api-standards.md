# معايير وقواعد تصميم وتطوير واجهات برمجة التطبيقات (Strict REST API Standards)

> **المرجع الإلزامي لتصميم، مراجعة، وبناء واجهات الـ REST API في النظام (Zero Exceptions Policy).**

تخضع جميع واجهات برمجة التطبيقات (APIs) في النظام للمعايير المعمارية الصارمة الموضحة أدناه لضمان الاستدامة، سهولة التوسع، وقابلية التنبؤ من قبل أي مطور أو نظام عميل (Web, Mobile, Third-Party).

---

## 1. التصميم حول الموارد لا الإجراءات (Resource-Oriented Architecture)

- **الروابط أسماء وليست أفعال (Nouns, Never Verbs)**:
  - يجب أن تشير الروابط دائمًا إلى **المورد** (Resource) كاسم بصيغة الجمع، ويُحظر تمامًا تضمين الأفعال في المسار.
  - ❌ **ممنوع قطعيًا**: `/getUsers`, `/deleteOrder`, `/fetchProducts`, `/createInvoice`, `/updateProfile`.
  - ✅ **الصحيح والمعتمد**: `/users`, `/orders`, `/products`, `/invoices`, `/profile`.
- **الاعتماد على أفعال HTTP للتعبير عن العمليات**:
  - `GET /orders`: جلب قائمة الطلبات.
  - `POST /orders`: إنشاء طلب جديد.
  - `GET /orders/{order}`: جلب تفاصيل طلب محدد.
  - `PUT /orders/{order}`: استبدال بيانات الطلب بالكامل.
  - `PATCH /orders/{order}`: تحديث جزئي لبيانات الطلب.
  - `DELETE /orders/{order}`: حذف الطلب.
- **تحديد عمق الموارد الفرعية (Resource Nesting Limit)**:
  - يُسمح بمستوى تداخل واحد فقط للعلاقات المباشرة الواضحة (`1 level deep`):
    - ✅ `GET /merchants/{merchant}/products`
    - ✅ `POST /orders/{order}/items`
  - يُمنع منعًا باتًا التداخل لأكثر من مستويين:
    - ❌ `/merchants/{id}/categories/{id}/products/{id}/reviews`
    - ✅ يتم تسطيح المسار (Flattening) للمورد النهائي: `GET /products/{product}/reviews`.
- **العمليات والتحويلات غير الـ CRUD (Business Actions & State Transitions)**:
  - عند الحاجة لتنفيذ أمر عملي (مثل إلغاء طلب، تأكيد دفعة، إسناد مهمة):
    - **الخيار الأول (المفضل - كمورد فرعي يمثل الأمر)**:
      - `POST /orders/{order}/cancel`
      - `POST /deliveries/{delivery}/assign`
      - `POST /invoices/{invoice}/pay`
    - **الخيار الثاني (تحديث حالة المورد عبر PATCH)**:
      - `PATCH /orders/{order}/status` مع تمرير `{"status": "cancelled", "reason": "..."}` في جسم الطلب.

## 2. قابلية التنبؤ والاتساق في بنية الروابط (Predictable & Uniform URIs)

- **صيغة الجمع القياسية (Plural Nouns)**:
  - تُكتب أسماء الموارد دائمًا بصيغة الجمع باللغة الإنجليزية: `/users`, `/categories`, `/wallets`, `/order-clusters`.
  - استثناء وحيد: الموارد المفردة بطبيعتها التي لا يوجد منها سوى سجل واحد للمستخدم الحالي (Singleton Resources)، مثل: `/profile`, `/settings`.
- **نمط تسمية المسارات (kebab-case)**:
  - يجب استخدام `kebab-case` (أحرف صغيرة مفصولة بشرطة) لكافة الكلمات المركبة في الروابط:
    - ✅ `/product-categories`, `/delivery-tasks`, `/order-clusters`
    - ❌ `/productCategories`, `/product_categories`, `/ProductCategories`
- **معرّفات واضحة في مسار التوجيه (Explicit Route Model Binding)**:
  - استخدام أسماء معبرة للمتغيرات: `{user}`, `{order}`, `{product}` بدلاً من `{id}` المبهم في تعريفات الراوت.
  - عند استخدام حقل غير المعرف الرقمي الأساسي، يتم توضيحه في الراوت: `/products/{product:slug}`.
- **مبدأ التوقع البديهي (Intuitive Guessability)**:
  - إذا كان المطور يعلم أن مسار جلب تفاصيل المستخدم هو `GET /api/v1/users/{user}`، فيجب أن يكون متأكدًا بنسبة 100% ودون قراءة التوثيق أن جلب تفاصيل المتجر هو `GET /api/v1/shops/{shop}`.

## 3. دلالات أفعال HTTP وإمكانية إعادة المحاولة (HTTP Method Semantics & Idempotency)

يجب الالتزام الصارم بدلالة كل فعل ومستوى أمانه وإمكانية تكراره:

| الفعل (HTTP Method) | الدلالة الوظيفية | آمن (Safe) | مكرر بأمان (Idempotent) | قابل للتخزين المؤقت (Cacheable) |
|---|---|---|---|---|
| **GET** | قراءة أو استعلام عن مورد | **نعم** | **نعم** | **نعم** |
| **POST** | إنشاء مورد جديد أو تشغيل أمر معقد | **لا** | **لا** | في حالات خاصة فقط |
| **PUT** | استبدال المورد بالكامل بنسخة جديدة | **لا** | **نعم** | **لا** |
| **PATCH** | تعديل حقول محددة فقط في المورد | **لا** | **نعم (بشكل عام)** | **لا** |
| **DELETE** | حذف المورد | **لا** | **نعم** | **لا** |
| **HEAD** | جلب ترويسات الرد فقط دون جسم (Body) | **نعم** | **نعم** | **نعم** |

- **حظر الآثار الجانبية في GET**:
  - يُحظر نهائيًا أن تقوم أي دالة مرتبطة بـ `GET` بأي تعديل في قاعدة البيانات، تغيير حالة، أو إرسال إشعارات وخصم مالي. الـ GET مخصص للقراءة الصافية فقط.
- **ضمان الـ Idempotency في العمليات الحرجة**:
  - العمليات المالية (المدفوعات، الإيداع، التحويل) والعمليات التي قد تتكرر تلقائيًا عند انقطاع الاتصال يجب أن تدعم ترويسة فريدة `Idempotency-Key` لمنع التنفيذ المزدوج.

## 4. الدلالة الدقيقة لرموز الحالة (Semantic HTTP Status Codes)

يُمنع منعًا باتًا إرجاع `200 OK` لجميع العمليات أو إخفاء رمز الفشل الحقيقي داخل جسم الرد (`response body`). يجب استخدام الرموز القياسية التالية:

### أ. النجاح (Success - 2xx)
- **`200 OK`**: عند نجاح عمليات القراءة (`GET`) أو التحديث الجزئي/الكامل (`PATCH` / `PUT`) التي ترجع بيانات الكائن المحدث.
- **`201 Created`**: عند نجاح إنشاء مورد جديد عبر (`POST`). يجب إرجاع بيانات المورد المنشأ وترويسة `Location` برابط المورد إن أمكن.
- **`204 No Content`**: عند نجاح العملية دون الحاجة لإرجاع أي محتوى في الرد (مثل `DELETE` الناجح، أو عمليات التفعيل السريعة).

### ب. أخطاء العميل (Client Errors - 4xx)
- **`400 Bad Request`**: عندما يكون الطلب مشوهاً، تركيبة الـ JSON خاطئة، أو الترويسات المطلوبة مفقودة.
- **`401 Unauthorized`**: عند غياب توكن المصادقة (Bearer Token)، أو انتهاء صلاحيته، أو كونه غير صالح.
- **`403 Forbidden`**: عندما يكون العميل مسجل الدخول بنجاح، لكنه **لا يملك الصلاحية** للوصول للمورد (Policy/Gate Denied).
- **`404 Not Found`**: المورد المطلوب غير موجود في قاعدة البيانات، أو الرابط غير معرّف في النظام.
- **`405 Method Not Allowed`**: عند استدعاء فعل HTTP غير مدعوم على الرابط (مثلاً إرسال `POST` إلى رابط للقراءة فقط).
- **`409 Conflict`**: عند حدوث تعارض منطقي في قواعد العمل (مثلاً: محاولة تعديل سجل أثناء معالجته بواسطة عملية أخرى، أو تكرار بريد مسجل مسبقاً، أو انتهاك تسلسل الحالات).
- **`422 Unprocessable Entity`**: فشل التحقق من صحة المدخلات (Validation Errors في الـ Form Request).
- **`429 Too Many Requests`**: تجاوز العميل لحدود معدل الطلبات المسموح بها (Rate Limiting).

### ج. أخطاء الخادم (Server Errors - 5xx)
- **`500 Internal Server Error`**: حدوث خطأ غير متوقع في الخادم (مع كتم تفاصيل الاستثناء في بيئة الإنتاج).
- **`503 Service Unavailable`**: الخادم تحت الصيانة أو تعذر الاتصال بخدمة أساسية تابعة كبوابة الدفع.

## 5. المعيار الموحد والمحمي لاستجابات الأخطاء (Structured Error Responses)

يجب أن تعود جميع الأخطاء الصادرة من النظام بتنسيق JSON موحد وثابت:

```json
{
  "success": false,
  "error": {
    "code": "ORDER_ALREADY_SETTLED",
    "message": "لا يمكن تعديل هذا الطلب لأنه تمت تسويته مالياً بالفعل",
    "details": {
      "order_id": 1420,
      "settlement_status": "completed"
    }
  }
}
```

- **المتطلبات الإلزامية في رد الخطأ**:
  1. `success: false`: مؤشر فوري منطقي.
  2. `error.code`: رمز نصي فريد ومقروء آلياً (Machine-Readable String) بأحرف كبيرة مفصولة بـ `_` (مثل `INSUFFICIENT_FUNDS`, `INVALID_COURIER_STATUS`).
  3. `error.message`: رسالة واضحة ومفهومة باللغة الحالية للمستخدم عبر نظام الترجمة.
  4. `error.details` (اختياري): كائن يحتوي على معطيات تشخيصية غير حساسة.
- **تنسيق أخطاء التحقق (422 Validation Errors)**:
  - عند فشل التحقق، يجب إرجاع مصفوفة الأخطاء تحت مفتاح `errors`:
  ```json
  {
    "success": false,
    "error": {
      "code": "VALIDATION_FAILED",
      "message": "البيانات المدخلة غير صالحة",
      "errors": {
        "email": ["البريد الإلكتروني مستخدم بالفعل"],
        "price": ["يجب أن يكون السعر قيمة موجبة"]
      }
    }
  }
  ```
- **حظر كشف البيانات الحساسة وأخطاء الـ SQL**:
  - يُحظر نهائيًا تسريب أي SQL Query، اسم جدول، Stack Trace، أو مفاتيح وبيانات شخصية (PII) داخل ردود الـ API الموجهة للمستخدم أو العميل الخارجي.

## 6. مسار الرابط للكيانات ومعاملات الاستعلام للتخصيص (Path vs Query Parameters)

- **المسار (URI Path) يحدد "ما هو المورد" فقط**:
  - المسار مخصص حصرًا لتحديد موقع وهوية المورد وعلاقاته التابعة: `/api/v1/shops/{shop}/orders`.
- **معاملات الاستعلام (Query Parameters) تحدد "كيفية جلب المورد"**:
  - كل ما يتعلق بالتصفية، البحث، الترتيب، واختيار الحقول يجب أن يمرر عبر `?param=value`:
    - **الفلترة (Filtering)**: `?status=delivered&courier_id=5&created_after=2026-01-01`
    - **البحث (Searching)**: `?search=أحمد`
    - **الترتيب (Sorting)**:
      - باستخدام إشارة السالب للترتيب التنازلي: `?sort=-created_at,price`
      - أو المعاملات الصريحة: `?sort_by=created_at&sort_direction=desc`
    - **التصفح (Pagination)**: `?page=2&per_page=15`
    - **تضمين العلاقات (Relationships Eager-Loading)**: `?include=customer,items,shipping_address`
    - **تحديد الحقول المرتجعة (Sparse Fieldsets)**: `?fields[orders]=id,reference_number,total_amount`

## 7. استراتيجية إدارة الإصدارات والتوافقية (API Versioning & Deprecation)

- **اعتماد الترقيم في المسار (URI Versioning)**:
  - جميع واجهات النظام العامة والداخلية يجب أن تبدأ ببادئة الإصدار: `/api/v1/...`.
  - عند وجود تعديل جذري لا يتوافق مع الأنظمة السابقة (Breaking Change)، يتم إطلاق إصدار جديد مستقل: `/api/v2/...`.
- **تعريف التغييرات غير المسببة لكسر التوافق (Non-Breaking Changes)**:
  - إضافة حقل جديد في الرد (Response).
  - إضافة نقطة نهاية (Endpoint) جديدة بالكامل.
  - إضافة معامل استعلام جديد اختياري (Optional Query Param).
  - هذه التغييرات لا تستوجب إنشاء إصدار جديد وتضاف مباشرة للإصدار الحالي.
- **تعريف التغييرات الكاسرة للتوافق (Breaking Changes - تمنع تمامًا بدون إصدار جديد)**:
  - إعادة تسمية أو حذف حقل موجود في الاستجابة.
  - تغيير نوع البيانات لحقل (مثلاً من `string` إلى `array`).
  - جعل معامل إدخال كان اختياريًا حقلًا إلزاميًا (Required).
  - تغيير دلالة رمز الحالة المرتجع لنقطة نهاية موجودة.
- **سياسة الإحالة للتقاعد (Deprecation Headers)**:
  - عند تقاعد أي إصدار أو نقطة نهاية، يجب إرسال ترويسات HTTP الرسمية في الرد:
    - `Deprecation: true`
    - `Sunset: Wed, 11 Nov 2026 00:00:00 GMT`

## 8. الاتساق الصارم في التنسيق وتغليف البيانات (Formatting & Envelope Standards)

- **تسمية المفاتيح (Key Casing)**:
  - نعتمد نمط `snake_case` دائمًا وموحدًا لكافة مفاتيح JSON في الطلب والاستجابة (Request & Response):
    - ✅ `{"reference_number": "ORD-123", "created_at": "...", "delivery_address": {...}}`
    - ❌ `{"referenceNumber": "ORD-123"}` أو `{"Reference_Number": "..."}`
- **تنسيق التواريخ والوقت**:
  - تلتزم جميع التواريخ بمعيار ISO 8601 الدولي بنطاق التوقيت العالمي (UTC):
    - `2026-09-08T10:12:49Z`
- **تمثيل القيم المالية والعملات (Money & Decimals)**:
  - يُمنع إرسال الأرقام المالية كأرقام عشرية عائمة خام (`floats`) لتفادي مشاكل الدقة الرياضية (Floating-Point Precision Issues).
  - تُرسل المبالغ بصيغة نصية دقيقة محددة الخانات أو كقيمة بالهللات/السنتات كـ `integer`، مع توضيح العملة دائمًا:
    ```json
    {
      "amount": "150.50",
      "amount_in_cents": 15050,
      "currency": "SAR"
    }
    ```
- **هيكل الاستجابة الناجحة المفردة (Single Resource Envelope)**:
  ```json
  {
    "success": true,
    "data": {
      "id": 1,
      "name": "اسم المورد"
    }
  }
  ```
- **هيكل استجابة التصفح الموحد (Paginated Resource Envelope)**:
  ```json
  {
    "success": true,
    "data": [ ... ],
    "meta": {
      "current_page": 1,
      "per_page": 15,
      "total": 120,
      "last_page": 8
    },
    "links": {
      "first": "https://api.domain.com/v1/orders?page=1",
      "last": "https://api.domain.com/v1/orders?page=8",
      "prev": null,
      "next": "https://api.domain.com/v1/orders?page=2"
    }
  }
  ```

## 9. التنسيق مع معمارية Laravel Modules في المشروع

- مسارات الـ API توضع في: `Modules/{ModuleName}/routes/api.php` مغلفة بـ `prefix('v1')` و `middleware(['auth:sanctum'])`.
- مدخلات الطلب يتم التحقق منها حصراً في: `Modules/{ModuleName}/app/Http/Requests/`.
- التحويل والعرض يتم حصراً في طبقة Transformers/Resources: `Modules/{ModuleName}/app/Transformers/`.
- منطق الأعمال يتم حصراً في Actions: `Modules/{ModuleName}/app/Actions/`.
- المتحكمات (Controllers) تبقى رفيعة جداً: `Request -> DTO -> Action -> Transformer -> Response`.

## 10. التوثيق الإلزامي للواجهات ومجلد `api-docs/` (Mandatory API Documentation & Grouping Rules)

> **القاعدة الصارمة: لا يُعتبر أي API مكتملاً برمجياً حتى يتم توثيقه بالكامل في ملف التوثيق المخصص له.**

### أ. موقع وهيكل التوثيق في المشروع
- يتم إنشاء مجلد مخصص للتوثيق في **المسار الرئيسي للمشروع حصراً**:
  `api-docs/`
- يحتوي المجلد على ملف فهرس رئيسي `api-docs/README.md` يربط كافة ملفات الخدمات ويوضح إرشادات الاستخدام وبيئة التشغيل ومفاتيح الاختبار.

### ب. قاعدة التجميع حسب الخدمة/المورد (Resource-Based Domain Grouping)
- **حظر الملف الواحد العملاق**: يُمنع منعًا باتًا جمع كافة واجهات النظام في ملف توثيق واحد شامل.
- **حظر تفتيت التوثيق لنقاط مفردة**: يُمنع إنشاء ملف لكل نقطة نهاية مفردة (مثل `get-order.md` أو `cancel-order.md`).
- **القاعدة المعتمدة (ملف موحد لكل خدمة/مورد)**:
  - كل نطاق عمل أو مورد (Resource Domain) يملك ملف توثيق واحد فقط بصيغة `.md` يضم كافة العمليات التابعة له (قراءة، إنشاء، تعديل، حذف، أوامر، تغيير حالات):
    - `api-docs/orders.md`: لكافة واجهات الطلبات.
    - `api-docs/products.md`: لكافة واجهات المنتجات والكتالوج.
    - `api-docs/couriers.md`: لكافة واجهات المناديب والتوصيل.
    - `api-docs/wallets.md`: لكافة واجهات المحافظ والعمليات المالية.
    - `api-docs/users.md`: لكافة واجهات إدارة المستخدمين والصلاحيات.
    - `api-docs/auth.md`: لكافة واجهات تسجيل الدخول والرموز المميزة.

### ج. التوثيق الفوري عند الإنجاز (Continuous Real-Time Documentation)
- بمجرد الانتهاء من برمجة أو تعديل أي API، يجب كتابة أو تحديث توثيقه فورًا في ملف التوثيق المطابق له قبل اعتبار المهمة منتهية.
- في حال وجود واجهة قيد التطوير ولم تكتمل بعد، تُوثق مع وسم حالتها بوضوح كـ `قيد التطوير`.

### د. العناصر الإلزامية لكل نقطة نهاية في التوثيق
يجب أن يتضمن توثيق كل نقطة نهاية التفاصيل التالية دون أي نقص:
1. **عنوان النقطة ووصفها الوظيفي**: توضيح دقيق للغرض من نقطة النهاية وسيناريو استخدامها.
2. **حالة الـ API (Lifecycle Status)**:
   - 🟢 `جاهز ومستقر (Ready / Stable)`: مكتمل ومختبر وجاهز للاستهلاك.
   - 🟡 `قيد التطوير (In Progress / Draft)`: جاري العمل عليه أو بانتظار استكمال أجزاء معينة.
   - 🟠 `محدّث / قيد المراجعة (Updated / Review)`: تم تعديل مدخلاته أو ردوده ويحتاج مراجعة.
   - 🔴 `متقاعد (Deprecated)`: نقطة نهاية قديمة سيتم إيقافها، مع توضيح البديل وموعد الإيقاف.
3. **الفعل والمسار الصريح (HTTP Method & URI)**: مثل `POST /api/v1/orders/{order}/cancel`.
4. **الصلاحيات والترويسات (Authentication & Headers)**:
   - تحديد متطلبات الـ Bearer Token والصلاحية المطلوبة (مثل `orders.cancel`).
   - الترويسات المطلوبة: `Accept: application/json`, `Content-Type: application/json`، بالإضافة لـ `Idempotency-Key` إن كانت العملية حساسة.
5. **معاملات الاستعلام (Query Parameters)** (إن وجدت): جدول يوضح اسم المعامل، نوعه، كونه إلزامي أم اختياري، والغرض منه.
6. **جسم الطلب (Request Body)**: مثال JSON صالح مع توضيح شروط التحقق لكل حقل.
7. **الردود المتوقعة الناجحة (Success Responses)**:
   - رمز الـ HTTP الدلالي (200, 201, 204).
   - مثال JSON واقعي وكامل للرد وفق مغلف الردود المعتمد في النظام (`ApiResponse`).
8. **ردود الأخطاء المتوقعة (Expected Error Responses & Error Codes)**:
   - جدول شامل يوضح كافة السيناريوهات التي قد تفشل فيها العملية:
     - رمز الـ HTTP (مثل 401, 403, 404, 409, 422).
     - الرمز الآلي المقروء للخطأ (`error.code` مثل `ORDER_ALREADY_CANCELLED`, `INSUFFICIENT_STOCK`).
     - سبب الخطأ ورسالة الخطأ التوضيحية.
     - نموذج JSON لرد الخطأ كما سيصل للعميل.
