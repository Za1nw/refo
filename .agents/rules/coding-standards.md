# معايير البرمجة الصارمة والقواعد المعمارية (Strict Coding Standards & Architecture Rules)

> **المرجع الإلزامي لكتابة، إعادة هيكلة، ومراجعة الأكواد البرمجية في النظام (Zero Exceptions Policy).**

يجب الالتزام التام وغير المشروط بالمبادئ الهندسية التالية أثناء كتابة أي كود في الباك إند أو الفرونت إند:

---

## 1. المسار السعيد وبنود الحماية (Happy Path & Guard Clauses - Flatten Structure)

- **منع التداخل العميق**: يُحظر نهائيًا استخدام كتل `if/else` المتداخلة بعمق (أقصى عمق مسموح به هو مستوى واحد فقط `1 level nesting`).
- **بنود الحماية (Guard Clauses)**: ضع دائمًا شروط الحماية في بداية الدوال للتعامل الفوري مع الحالات الحدية، فشل التحقق، أو الإرجاع المبكر (`early return` أو رمي استثناء مبكر).
- **المسار السعيد الخطي**: اجعل منطق العمل الأساسي (Core Business Logic) غير متفرع داخل أقواس متداخلة، واجعله يسير خطيًا وبشكل مستوٍ تمامًا على طول المسار السعيد.

```php
// ❌ خطأ (تداخل غير مبرر):
if ($customer->isActive()) {
    if ($order->hasStock()) {
        if ($payment->process()) {
            return $order->complete();
        } else {
            throw new PaymentFailedException();
        }
    }
}

// ✅ صحيح (Guard Clauses ومسار سعيد مستوٍ):
if (! $customer->isActive()) {
    throw new InactiveCustomerException();
}

if (! $order->hasStock()) {
    throw new OutOfStockException();
}

$payment->process();

return $order->complete();
```

## 2. التسميات السياقية والمعبرة (Context-Driven & Expressive Naming)

- **حظر الأسماء العامة**: يُمنع منعًا باتًا استخدام أسماء مبهمة أو عامة مثل: `data`, `item`, `res`, `result`, `temp`, `val`, `obj`.
- **بيان الدور الوظيفي بدقة**: يجب أن تعكس كافة المعرّفات (متغيرات، دوال، كلاسات، معاملات) وظيفتها ونطاق عملها التجاري (Business Domain) بوضوح تام، مثل:
  - `verifiedCustomer` بدلاً من `user` أو `c`
  - `pendingRefundOrders` بدلاً من `list` أو `data`
  - `calculateAnnualTax()` بدلاً من `calc()` أو `doProcess()`
- **كود ذاتي التوثيق (Self-Documenting)**: يجب أن يوضح الاسم محتواه وهدفه دون الحاجة لقراءة تعليق جانبي لمعرفة ماذا يمثل هذا المتغير أو الدالة.

---

## 3. عزل الأنظمة الخارجية وطبقة مكافحة الفساد (External System Isolation - Anti-Corruption Layer)

- **منع تسريب المخططات الخارجية**: يُمنع كشف حمولات الـ APIs الخارجية (Third-Party Payloads)، أو نماذج قواعد البيانات الخام، أو عقود الشركاء مباشرة داخل طبقات العمل والخدمات الداخلية (Internal Domain Services).
- **طبقة المحول (Adapter/Mapper Layer)**: يجب بناء كائنات نقل بيانات (DTOs) أو محولات (Adapters/Mappers) عند حدود النظام (System Boundaries) تقوم فورًا بتحويل الحمولات الخارجية الخام إلى كائنات ونماذج نطاق داخلية واضحة ومحددة.
- **حصر التعديلات**: إذا طرأ أي تغيير على هيكل بيانات الشريك الخارجي أو الـ API الخارجي، يجب أن ينحصر التعديل بالكامل داخل طبقة الـ Adapter دون المساس بالمنطق الداخلي للتطبيق.

---

## 4. جعل الحالات غير الصالحة مستحيلة التمثيل (Make Illegal States Unrepresentable)

- **منع إنشاء حالات عمل غير صالحة**: صمم الأنواع والـ Schemas والكائنات بطريقة تمنع النظام برمجياً ومنطقياً من إنشاء كائن بحالة عمل متناقضة أو غير صالحة.
- **تجنب الأنواع العريضة الفضفاضة (Wide Types)**: تجنب الاعتماد على كائنات مليئة بالحقول الاختيارية القابلة للقيمة الفارغة (`string?`, `number?`, `null`) لتمثيل دورات حياة معقدة ومتعددة المراحل.
- **التباين المطبوع (Discriminated Unions / Typed State Variants)**:
  - استخدم كائنات حالة منفصلة ومحددة بدقة لكل مرحلة.
  - مثال: فصل `PendingOrder` عن `PaidOrder`، حيث يضمن نوع `PaidOrder` وجود حقل `transactionId: string` كحقل إلزامي غير قابل للـ `null`، بدلاً من جعل `transactionId` اختياريًا في كائن طلب وحيد.

---

## 5. فصل القرارات عن الآثار الجانبية (Separation of Decisions from Effects - Pure Logic vs. Side Effects)

- **عزل المنطق النقي عن الآثار الجانبية**: افصل منطق اتخاذ القرارات الحسابية أو قواعد العمل (Business Decision Logic) تمامًا عن عمليات الإدخال والإخراج (I/O)، اتصالات قواعد البيانات، مكالمات الشبكة، أو إرسال الإشعارات.
- **هيكلة سير العمل الخطي**:
  1. **التجميع (Gather Inputs)**: جلب المدخلات المطلوبة من قاعدة البيانات أو المصادر الخارجية.
  2. **القرار النقي (Pure Decision Function)**: تمرير المدخلات إلى دالة نقية خالية من الآثار الجانبية ترجع القرار (سهلة الفحص التلقائي بالـ Unit Tests دون الحاجة لـ Mocks معقدة).
  3. **تنفيذ الأثر (Execute Side Effects)**: تنفيذ عمليات الحفظ والإرسال والإشعار بناءً على مخرجات دالة القرار.

---

## 6. المعالجة الغنية والقابلة للتتبع للأخطاء (Actionable & Rich Error Handling)

- **حظر الاستثناءات العامة**: يُمنع رمي استثناءات عامة أو رسائل فارغة أو مبهمة مثل `"Something went wrong"`.
- **المتطلبات الإلزامية لكل خطأ**:
  1. **رمز آلي مقروء (Machine-Readable String Code)**: مثل `ORDER_ALREADY_SETTLED`, `INSUFFICIENT_WALLET_BALANCE`.
  2. **سياق تشخيصي دقيق (Diagnostic Context)**: معرفات الكيانات المتأثرة، الحالة المتوقعة مقابل الحالة المستلمة (Expected vs. Received).
- **حماية البيانات الحساسة**: يُمنع منعًا باتًا تسجيل أو طباعة أو كشف أي بيانات حساسة (كلمات المرور، التوكنات، مفاتيح التشفير، أو بيانات الهوية الشخصية PII) داخل سجلات الأخطاء (Logs) أو حمولات الـ Exceptions المرتجعة للمستخدم.

---

## 7. النطاق الذري والمركز (Atomic & Focused Scope)

- **مسؤولية واحدة محددة (Single Responsibility)**: يجب أن تكون الدوال والموديولات والتغييرات البرمجية صغيرة ومركزة وتؤدي عملاً واحداً ومحدداً بدقة.
- **منع خلط المهام**: يُحظر دمج إعادة هيكلة غير مترابطة أو ميزات إضافية متعددة داخل طلب واحد أو دالة واحدة.
- **التغييرات الذرية (Atomic Changes)**: تأكد من أن كل تعديل قابل للاختبار والمراجعة والتراجع الآمن (Rollback Safety) دون التأثير على أجزاء غير متعلقة بالنظام.

---

## 8. توثيق وتعليقات الكود القياسية باللغة العربية (Standard Arabic Code Documentation)

- **اللغة الإلزامية للتعليقات**: جميع التعليقات التوضيحية داخل الكود وكتل التوثيق القياسية (PHPDoc / TSDoc / JSDoc / Inline Comments) يجب أن تكون **باللغة العربية الفصحى الواضحة والمهنية**.
- **معايير التوثيق القياسي (DocBlocks)**:
  - **في الباك إند (PHP / Laravel)**: استخدام كتل PHPDoc (`/** ... */`) لتوثيق الكلاسات والواجهات والدوال مع توضيح:
    - الغرض من الدالة أو الكلاس بالعربية.
    - المعاملات `@param` مع وصف وظيفي لكل معامل.
    - القيمة المرتجعة `@return` مع توضيح دلالتها.
    - الاستثناءات المحتملة `@throws` مع ذكر سبب حدوثها.
  - **في الفرونت إند (TypeScript / React)**: استخدام كتل TSDoc / JSDoc القياسية لتوثيق الواجهات (Interfaces)، الهوكات المخصصة (Custom Hooks)، والخصائص (Props).
- **التركيز على "لماذا" وليس "ماذا" (Document Why, Not What)**:
  - التسميات المعبرة والكود النظيف يشرحان "ماذا" يفعل الكود (القاعدة 2).
  - تُستخدم التعليقات العربية لشرح **الأسباب، القرارات المعمارية، قواعد العمل المعقدة، والتحذيرات من الحالات الاستثنائية**.
  - تجنب كتابة تعليقات بديهية تكرر ما هو واضح من سياق الكود (مثل: `// زيادة العداد بمقدار 1: $count++`).
- **العلامات التحذيرية والمهام القياسية**:
  - `// تنبيه: ...` للتحذير من آثار جانبية أو قيود تقنية حساسة.
  - `// ملاحظة معمارية: ...` لتوضيح سبب اعتماد تصميم معين.
  - `// TODO: ...` مع وصف دقيق باللغة العربية للمهمة المتبقية وشروط إكمالها.

```php
/**
 * حساب العمولة المستحقة لمندوب التوصيل بناءً على مسافة الشحنة ونوع المركبة.
 *
 * سبب معماري: يتم فصل حساب العمولة في دالة نقية تماشياً مع قاعدة فصل القرارات
 * عن الآثار الجانبية لتسهيل اختبار السيناريوهات المختلفة بدون اتصال بقاعدة البيانات.
 *
 * @param  CourierProfile  $courierProfile  الملف التعريفي للمندوب شاملاً رتبته الحالية
 * @param  DeliveryDistance  $deliveryDistance  مسافة التوصيل المقطوعة بالكيلومتر
 * @return CommissionAmount  المبلغ الصافي للعمولة المستحقة
 *
 * @throws InvalidDistanceException إذا كانت مسافة التوصيل سالبة أو تتجاوز الحد الأقصى للنطاق
 */
public function calculateCourierCommission(
    CourierProfile $courierProfile,
    DeliveryDistance $deliveryDistance
): CommissionAmount {
    // التحقق من صلاحية المسافة قبل بدء العمليات الحسابية
    if ($deliveryDistance->isNegative()) {
        throw new InvalidDistanceException(
            code: 'INVALID_DELIVERY_DISTANCE',
            message: 'مسافة التوصيل لا يمكن أن تكون قيمة سالبة',
            context: ['distance' => $deliveryDistance->value()]
        );
    }

    return $this->commissionCalculator->compute($courierProfile, $deliveryDistance);
}
```
